## 1. Продукт и ценностное предложение

T-SQL Formatter — бесплатное расширение для Visual Studio 2022/2026 и SSMS 20/22
с CLI для CI. Ядро ценности сегодня — единый корпоративный стиль SQL:
форматирование документа/выделения по настраиваемым профилям, импорт профилей
из SQL Prompt и SQL Complete, пакетная проверка и запись в CI.

Развитие направлено на то, чтобы после форматирования команда могла опираться
на те же механизмы для **контроля качества** (статический анализ), **скорости
написания** (сниппеты, генерация, преобразования) и **безопасности**
(восстановление работы, защита от опасных команд в продуктиве).

## 2. Целевые пользователи и сценарии

- **Разработчик БД** в SSMS/VS: ежедневное написание и ревью T-SQL, длинные
  скрипты миграций, типовые процедуры.
- **Ревьюер/лид команды**: единый стиль и автоматический контроль типовых ошибок
  до ревью и в CI.
- **DevOps/CI**: проверка форматирования и (после фазы 1) замечаний анализатора
  в пайплайнах без установки IDE.

## 3. Текущие возможности

- Форматирование документа, выделения; контекстное меню; отмена одной операцией.
- Настройки: именованные профили, группы правил, предпросмотр, RU/EN интерфейс.
- Импорт/экспорт профилей, в том числе конвертированные профили SQL Prompt
  (ADIR) и SQL Complete (AV, EPM, нативные альтернативы).
- CLI: stdin/файлы/каталоги, `--write`/`--check`, dotnet tool для CI.
- В исходниках текущей ветки: `--analyze` и команды анализа, сниппеты,
  переименование, навигация, преобразования, CRUD по CREATE TABLE и история при
  сохранении. Эти функции ещё не включены в дистрибутивы release/.
- Четыре установочных пакета: VS 2022, VS 2026, SSMS 20, SSMS 22.

## 4. Конкурентное позиционирование

Сопоставление с SQL Prompt (Redgate) и SQL Complete (Devart) по итогам анализа
их официальных материалов (обсуждение с codex, октябрь 2026). Направления
отобраны по соотношению «ценность/сложность на текущей архитектуре».

| Направление | SQL Prompt | SQL Complete | Наш план |
|---|---|---|---|
| Статический анализ | да, +автоисправления | да | Фаза 1: правила, серьёзность, редактор и CI |
| Сниппеты | да | да | Фаза 2: встроенные + пользовательские JSON |
| Переименование переменных/алиасов | да | да | Фаза 2: batch/запрос-область, предпросмотр |
| Преобразования SQL | да | частично | Фаза 2: ограниченный набор с предпросмотром |
| Структура скрипта, навигация | да | да | Фаза 2: дерево скрипта, переход к объявлению |
| Автодополнение по схеме БД | да | да | Вне текущей дорожной карты (требует слой метаданных) |
| Генерация CRUD по таблице | частично | да | Фаза 3: из CREATE TABLE, без живого подключения |
| История/восстановление работы | да | да | Фаза 3: локальные снимки, поиск, восстановление |
| Цвета окружений, предупреждения | частично | да | Фаза 3: метки DEV/TEST/PROD, проверка опасных команд |
| Работа с результатами запросов | да | да | Фаза 3: TSV из буфера → IN/INSERT/статистика |

Сильная сторона проекта: открытость (репозиторий), локальность (без облака),
CLI для CI и конвертация уже существующих профилей команд, купивших
SQL Prompt/SQL Complete ранее.

## 5. Дорожная карта развития

Актуальные статусы — в [`ROADMAP.md`](ROADMAP.md). Кратко:

- **Фаза 1 — Статический анализ** (этапы 1–3): ядро правил → CLI `--analyze` →
  подсказки в редакторе.
- **Фаза 2 — Инструменты редактора** (этапы 4–7): сниппеты → переименование →
  структура скрипта → преобразования.
- **Фаза 3 — Метаданные и возможности SSMS** (этапы 8–11): генерация CRUD →
  история → окружения → работа с результатами.
- **Этап 12** — консолидированный выпуск и финальная документация.

## 6. Ценность новых возможностей по фазам

Раздел заполняется по завершении фаз: сценарии «до/после», измеримые эффекты
(время на ревью, доля замечаний, ловимых автоматически, восстановление потерянного
кода), история внедрения по этапам.

### Фаза 1 — Статический анализ *(реализованы ядро, CLI и настройки редактора)*

Готово ядро анализатора: пять правил первой очереди — `SELECT *`, `INSERT` без
списка колонок, `TOP` без `ORDER BY`, `UPDATE`/`DELETE` без `WHERE`. Для
`UPDATE`/`DELETE` без `WHERE` серьёзность по умолчанию — ошибка (риск массовой
потери данных), остальные — предупреждения; любую серьёзность можно изменить, а
отдельное правило — точечно отключить.

CLI-проверка `tsqlformat --analyze` работает для stdin, одиночных файлов и
каталогов, поэтому контроль качества SQL встраивается в CI без установки IDE:
код выхода 1 ломает сборку при замечаниях, формат вывода
`путь(строка,столбец): КОД [серьёзность] сообщение` удобен для разбора в
пайплайнах.

В редакторах VS и SSMS команда «Проанализировать документ» подчёркивает находки
и открывает отчёт с переходом к месту замечания — те же правила и та же
конфигурация `analysis`, что и в CI. Ценность фазы: типовые замечания видны до
ревью в трёх точках (редактор, CI, CLI) с единой настройкой.

Оценка эффекта на реальном коде (доля типовых замечаний, ловимых автоматически)
не измерялась. Проверки текущих исходников в установленных VS/SSMS описаны в
[отчёте этапов 3 и 9](stages-3-9-validation.md); текущие пакеты VS 0.2.13 / SSMS
0.6.12 и границы их проверки описаны в [проверке выпуска](../../release/VALIDATION.md).

### Фаза 2 — Инструменты редактора *(все 4 этапа выполнены)*

Сниппеты SQL: пять встроенных шаблонов (процедура с TRY/CATCH, TRY/CATCH, транзакция
с ROLLBACK, SELECT с JOIN, INSERT) и пользовательские JSON-шаблоны в локальном
каталоге `%USERPROFILE%\.tsqlformatter\snippets` — типовые заготовки вставляются за
секунды с навигацией по параметрам и одной отменой.

Переименование переменных и алиасов: безопасный рефакторинг с предпросмотром —
все вхождения (`@переменной` в batch, алиаса с уточнениями колонок в запросе,
включая коррелированные ссылки) меняются одной операцией Undo; корректно
обрабатывается затенение одноимённым алиасом во вложенном запросе.

Структура скрипта и навигация: дерево batch/модулей/операторов/CTE/переменных с
переходом в один клик и «Перейти к объявлению» для переменных — ориентировка в
длинных скриптах миграций и чужих процедурах перестаёт требовать прокрутки
всего файла.

Преобразования SQL с предпросмотром: INSERT→UPDATE, VALUES→UNION ALL и
перехват кода возврата EXEC — рутинная переработка операторов выполняется
корректно (результат собирается из AST и сразу форматируется профилем команды)
и обратимо одной отменой, вместо ручного редактирования с риском сломать
синтаксис.

Фаза 2 закрыта.

### Фаза 3 — Метаданные БД и возможности SSMS *(этапы 8–9 реализованы)*

Генерация CRUD по `CREATE TABLE`: команда разбирает структуру таблицы из скрипта
(без живого подключения к БД) и вставляет заготовки SELECT/INSERT/UPDATE/DELETE и
процедуру Upsert, отформатированные профилем команды, с предпросмотром и одной
отменой. IDENTITY-колонки исключаются из изменяемых частей; WHERE-заглушки явно
помечены `/* TODO: key */`, чтобы генерация не создавала ложного ощущения готовых
запросов. Это ускоряет написание типового кода доступа и снижает число опечаток
в именах колонок и типов.

Впереди: окружения и защита от опасных команд (этап 10), работа с результатами
запросов (этап 11) и консолидированный выпуск (этап 12).
Промежуточные пакеты завершённых этапов 1–9 поставлены 2026-10-31; ждать
реализации этапов 10–11 для установки анализа и истории не требуется.

### История редактора (этап 9)

История сохраняет локальные версии при сохранении и закрытии SQL-документа, включая
отброшенные несохранённые правки. Сбор независим от форматирования; поиск и предпросмотр
помогают восстановить текст в новом документе. Пользователь задаёт число снимков, размер,
срок хранения и может отключить сбор без удаления существующей истории.

В настройках анализа доступны включение, пять правил и серьёзности с единым форматом
analysis в проекте. Настройки проекта перекрывают явно заданные поля поверх настроек IDE.
Профили форматирования остаются независимыми. Метаданные сервера/БД сохраняются только
при доступности контекста SSMS; пароли не сохраняются, соединения не открываются.

Результаты установленных проверок и ограничения платформ: [проверка этапов 3 и 9](stages-3-9-validation.md).

### Исторические результаты проверки 2026-10-30

На 2026-10-30 этап 3 не был завершён: правила настраивались только через JSON.
Остаток реализован 2026-10-31; текущие результаты приведены в отчёте выше.
Исправлены сохранение условия IF/ELSE/WHILE при преобразовании EXEC, запрет
зарезервированных алиасов, экранирование генерируемых имён и коллизии снимков.
Тогда изменения были проверены регрессиями без установленной валидации.
На момент той проверки функции были доступны только в исходниках. Промежуточный
выпуск 2026-10-31 уже включает их в `release/`; финальный этап 12 остаётся впереди.

## 7. Ограничения и риски

- Автодополнение по живой схеме БД и отладчик T-SQL — вне текущей дорожной карты:
  требуют отдельной инфраструктуры (слой метаданных, серверные требования).
- Интеграции, зависящие от недокументированных API SSMS (окрашивание вкладок,
  перехват выполнения, прямой доступ к гриду результатов), выполняются по
  принципу best-effort с фиксацией фактического результата (ADR 0005).
- Все данные (история, снимки) — строго локальные; облачных компонентов нет.
