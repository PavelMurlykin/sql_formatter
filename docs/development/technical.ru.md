## 1. Обзор системы

T-SQL Formatter — расширение для Visual Studio 2022/2026 и SSMS 20/22 плюс CLI,
форматирование T-SQL по настраиваемым профилям. Компоненты:

| Компонент | Целевая платформа | Ответственность |
|---|---|---|
| `TSqlFormatter.Core` | netstandard2.0 | Разбор (ScriptDom), модель layout-документа, рендеринг, правила форматирования; без IDE-зависимостей (ADR 0003) |
| `TSqlFormatter.Configuration` | netstandard2.0 | Форматирование опций, JSON-конфигурация `.tsqlformatter.json`, профили, обмен профилями SQL Prompt/SQL Complete |
| `TSqlFormatter.Cli` | .NET 10 | CLI: stdin/файл/каталог, `--write`/`--check`, локальный dotnet tool (ADR 0007) |
| `TSqlFormatter.IdeShared` | net4x/netstandard2.0 | Общая UI-логика настроек и окон для IDE-адаптеров |
| `TSqlFormatter.VisualStudio` + `VisualStudio2022`, `Ssms`, `Ssms20` | net472 VSSDK | Команды редактора, страница настроек, события сохранения; SSMS — best-effort (ADR 0005) |

Ключевые принципы: Core не знает об IDE; редакторские команды захватывают
снапшот текста, работают в фоне и применяют результат в UI-потоке одной
undo-транзакцией (ADR 0006).

## 2. Архитектура форматирования

Конвейер:

```
SQL-текст
  → ScriptDomSqlParser (Parsing/)        — AST, токены, тривиа (комментарии)
  → SqlParseResult                       — дерево + карта строк SqlLineMap
  → Builders (Formatting/Builders/)      — AST → Doc-модель (Layout/)
  → DocRenderer (Layout/)                — Doc → текст с учетом ширины строки
  → TextEdit[]                           — минимальные правки для редактора
```

- `ISqlParser`/`ScriptDomSqlParser` — разбор и диагностики разбора (`ParseDiagnostic`).
- `SqlSyntaxPolicy` — AST-based синтаксические политики (точки с запятой,
  необязательные квадратные скобки).
- `Formatting/*Options` + `RuleCatalog`/`RuleConfigurationV2` — настройки и профили.
- `EditorSqlFormatter` — фасад для IDE: принимает `FormatRequest`, возвращает
  `FormatResult` с правками; используется командами форматирования документов.

### 4.1. Статический анализ SQL — этапы 1–3 *(этап 1 выполнен)*

**Ядро (этап 1).** Каталог `src/TSqlFormatter.Core/Analysis/`:

| Тип | Назначение |
|---|---|
| `SqlAnalyzer` | фасад: принимает `SqlParseResult`, прогоняет включённые правила, сортирует диагностику по смещению, затем по коду |
| `IAnalysisRule` / `AnalysisRuleBase<TFragment>` | контракт правила и базовый класс с посетителем AST |
| `AnalysisDiagnostic` | код, серьёзность, сообщение, `SqlTextSpan`, строка/колонка (1-based, через `SqlLineMap`) |
| `AnalysisFinding` | «сырая» находка правила до применения настроек |
| `AnalysisOptions` | отключение правил по коду и переопределение серьёзности; коды сравниваются без учёта регистра |
| `AnalysisResult` | итоговый список диагностики (`HasDiagnostics`) |

Правила в `Analysis/Rules/` (коды стабильны, дальше используются в CLI и настройках):

| Код | Правило | Серьёзность по умолчанию |
|---|---|---|
| TSQL001 | `SELECT *`, включая квалифицированные `t.*` и звёзды в подзапросах; `COUNT(*)` не считается находкой | Warning |
| TSQL002 | `INSERT` без списка колонок; `DEFAULT VALUES` не считается нарушением | Warning |
| TSQL003 | `TOP` без `ORDER BY` в том же запросе; `ORDER BY` на уровне UNION не детерминирует строки `TOP`-ветки | Warning |
| TSQL004 | `UPDATE` без `WHERE` | Error |
| TSQL005 | `DELETE` без `WHERE` | Error |

Поведение: при неудачном разборе (`Root == null`) анализ возвращает пустой
результат — ошибки разбора остаются в `SqlParseResult.Diagnostics`; проверка
токена отмены выполняется при обходе AST.

Как добавить правило: унаследоваться от `AnalysisRuleBase<TFragment>` с нужным
типом узла (или реализовать `IAnalysisRule` напрямую), задать код и серьёзность
по умолчанию, добавить класс в `SqlAnalyzer.DefaultRules` или собрать
`SqlAnalyzer` со своим набором правил; покрыть тестами в
`tests/TSqlFormatter.Core.Tests/SqlAnalyzerTests.cs`.

Тесты: `SqlAnalyzerTests` — 26 сценариев: срабатывание каждого правила,
отсутствие ложных срабатываний (CTE с собственным `ORDER BY`, `COUNT(*)`,
`DEFAULT VALUES`, квалифицированные списки колонок), сортировка и номера строк,
отключение правила, переопределение серьёзности, null-root, отмена, контракты
аргументов.

**CLI `--analyze` (этап 2).** Режим в `src/TSqlFormatter.Cli/SqlFormatterCli.cs`
(`RunAnalyzeAsync`): stdin (`- --analyze`), одиночный файл и каталоги/наборы путей
с рекурсивным выбором `.sql` и `--exclude` (общий механизм `FindSqlFiles` с `--check`).
Замечания — в stdout строкой `путь(строка,столбец): КОД [серьёзность] сообщение`
(для stdin путь `-`); ошибки разбора — `TSF1000` в stderr. Коды выхода: 0 — замечаний
нет, 1 — есть замечания, 2 — ошибки ввода/разбора/конфигурации. `--analyze`
не комбинируется с `--write`/`--check`.

Конфигурация: необязательная секция `analysis` в `.tsqlformatter.json`
(версии 1 и 2): `disabled` — массив кодов правил, `severity` — объект
«код → info|warning|error» (без учёта регистра). Разбор —
`TSqlFormatter.Configuration/AnalysisConfigurationParser` (коды ошибок TSF2000),
модель `AnalysisConfiguration.ToAnalysisOptions()`. Валидатор настроек принимает
секцию `analysis` как известное свойство корня и не проверяет её содержимое —
это делает специализированный парсер; конфигурация ищется для каждого файла тем же
`SqlFormatterConfigurationDiscovery`, что и для форматирования; для stdin — правила
по умолчанию.

Тесты: `AnalysisConfigurationParserTests` (12 сценариев разбора секции и
совместимости с версиями 1/2) и `CliAnalyzeTests` (13 сценариев: stdin/файл/каталог,
`--exclude`, конфигурация, ошибки, коды выхода).

**Интеграция в редактор VS/SSMS (этап 3).** Общие компоненты в
`src/TSqlFormatter.IdeShared/` (общий исходный каталог обоих пакетов):

- `SqlDocumentAnalysis.Run(filePath, source, ct)` — снимок → правила из ближайшего
  `.tsqlformatter.json` (discovery + `AnalysisConfigurationParser`) → разбор (Auto) →
  `SqlAnalyzer`; ошибки — `TSF1000` (разбор) / `TSF9000` (конфигурация); на выходе
  диагностика + `SqlLineMap` для конечных позиций.
- `SqlAnalysisMarkers` — подчёркивания через `IVsTextLines.CreateLineMarker` с типом
  `MARKERTYPE.MARKER_CODESENSE_ERROR` по диапазону находки (1-based строка/колонка
  переводятся в 0-based); очистка — `Invalidate()` всех сохранённых маркеров.
- `AnalysisReportWindow` — немодальный WinForms-отчёт (позиция/код/серьёзность/сообщение,
  RU/EN), двойной клик/Enter → событие `Navigate`.
- `SqlEditorNavigation.GoTo` — `SetCaretPos` + `SetSelection` + `CenterLines`.

Команды (ID в обоих `Commands.vsct`, CommandSet своего пакета): `0x0210`
«Проанализировать документ» (меню и контекстное меню редактора, видимость — активный
`.sql`), `0x0211` «Очистить замечания анализа» (видимость — есть маркеры). Потоковая
модель как у форматирования: снапшот в UI-потоке → `Task.Run` → возврат в UI-поток →
проверка `ReferenceEquals(buffer)` перед маркерами; буфер ≤ 16 Ми символов.
Управление правилами — только секция `analysis` в `.tsqlformatter.json` (единый
источник с CLI); отдельная страница настроек не вводилась — зафиксировано как решение
этапа. Контракт меню покрыт тестом `SettingsPresentationTests` (4 кнопки, 2
context-размещения). Сборка всех четырёх VSIX и `Verify-Vsix.ps1` проходят;
валидация в установленном хосте не проводилась (AGENTS.md).

### 4.2. Инструменты редактора — этапы 4–7 *(этап 4 выполнен)*

**Сниппеты (этап 4).** Ядро в `src/TSqlFormatter.Core/Snippets/`:

| Тип | Назначение |
|---|---|
| `SqlSnippet` | имя, ярлык (без пробелов, может быть пустым), тело, описание; ключ слияния — ярлык либо имя (без учёта регистра) |
| `SnippetJson` | разбор JSON: объект или массив объектов `name`/`shortcut`/`description`/`body`, строгая валидация |
| `SnippetExpander` | раскрытие `$имя$`: плейсхолдер заменяется текстом имени, вхождения собираются как `SqlTextSpan` в порядке навигации; одиночный `$` и имена с пробелами остаются литералами |
| `SnippetStore` | встроенные 5 шаблонов (`proc`, `try`, `tran`, `select`, `insert`) + `*.json` из `%USERPROFILE%\.tsqlformatter\snippets` (каталог создаётся при загрузке); пользовательские заменяют встроенные по ключу, некорректные файлы пропускаются |

Интеграция: IdeShared `SnippetPickerWindow` (модальный диалог с фильтром по
ярлыку/имени/описанию) и `SnippetInsertionSession` (сессия навигации по параметрам,
активна, пока снапшот буфера не менялся). Команда `0x0220` «Вставить сниппет» в VS и
SSMS: загрузка стора в фоне, вставка в каретку/выделение одной undo-транзакцией,
выделение первого параметра; повторный вызов команды циклически переходит к следующему
параметру (Tab-фильтр не вводился — зафиксировано). Загрузка стора при каждом вызове
обеспечивает подхват пользовательских файлов без перезапуска IDE. Core получил ссылку
на Newtonsoft.Json (в VSIX сборка уже поставлялась через Configuration).

Тесты: `SnippetStoreTests`/`SnippetExpanderTests` — 25 сценариев (встроенный набор,
слияние и переопределение, пропуск некорректных файлов, создание каталога, разбор
JSON, раскрытие параметров и литеральные `$`), плюс контракт меню в
`SettingsPresentationTests` (5 кнопок, 3 context-размещения).

**Переименование (этап 5).** Ядро в `src/TSqlFormatter.Core/Refactoring/`:
`RenameAnalyzer.FindSymbol(parseResult, offset)` находит символ под смещением
(токен `@переменной` или идентификатор алиаса/квалификатора) и собирает вхождения;
`Plan(symbol, newName)` валидирует имя (`RenameNames`: переменная `@`+идентификатор,
алиас — идентификатор) и отображает вхождения в `TextEdit`.

Область видимости: переменная — свой `TSqlBatch` (объявление `DeclareVariableElement`
плюс все `VariableReference`); алиас — `QuerySpecification`, объявивший его
(`AliasScope`): одноимённые декларации и квалификаторы колонок связываются с ближайшей
декларацией по цепочке вложенных запросов, поэтому вложенный одноимённый алиас
затеняет внешний, а коррелированные ссылки из подзапросов попадают во внешний
символ. Учитываются квалификаторы `ColumnReferenceExpression` и `SelectStarExpression`.
Не поддерживаются: закавыченные алиасы, алиасы вне `QuerySpecification` (UPDATE/DELETE).

Интеграция: команда `0x0230` в VS и SSMS — разбор в фоне по снапшоту, диалоги
IdeShared `RenamePromptWindow` (валидация по виду символа) и `RenamePreviewWindow`
(позиция/было/станет через `SqlLineMap`), применение через новый метод
`TryApplyEdits` (несколько замен одной undo-транзакцией) в `ActiveSqlEditor`/
`ActiveQueryEditor`.

Тесты: `RenameAnalyzerTests` — 30 сценариев (переменные с batch-границей и SET/SELECT
ссылками, алиасы с квалификаторами SELECT/WHERE, изоляция запросов, затенение,
коррелированные ссылки, неподдерживаемые случаи, валидация имён, Plan/исключения);
контракт меню расширен до 6 кнопок и 4 context-размещений.

**Структура скрипта и навигация (этап 6).** Ядро в
`src/TSqlFormatter.Core/Navigation/`: `ScriptOutlineBuilder.Build(parseResult)` —
дерево `ScriptOutlineNode` (Script → Batch → Module/Statement → Cte/Variable);
span узла указывает на имя (переменная — имя в `DECLARE`, модуль — полное имя
объекта), тела модулей и `IF`/`WHILE`/`BEGIN…END` раскрываются рекурсивно;
`SymbolLocator.FindVariableDeclaration(parseResult, offset)` — ближайшее объявление

Интеграция: команды `0x0240` «Структура скрипта» (немодальное IdeShared-окно
`ScriptOutlineWindow` с деревом; двойной клик/Enter → `SqlEditorNavigation.GoTo`;

Показ owner-окон вынесен в синхронный хелпер `ShowOwned` (VSTHRD103 запрещает
синхронный `GetService` в async-методах).

Тесты: `NavigationTests` — 11 сценариев (дерево с batch/DECLARE/CTE, модули с
именами и телами, вложенные IF/BEGIN, span имён, null-root, ближайшее объявление,
объявление ниже/в другом batch, не-переменная, контракты); контракт меню —
8 кнопок и 5 context-размещений.

**Преобразования SQL (этап 7).** `src/TSqlFormatter.Core/Refactoring/SqlTransformer.cs`:
`Transform(kind, source, offset, options, ct)` находит минимальный оператор под смещением,
перестраивает его AST и генерирует текст через `Sql150ScriptGenerator`, затем заменяет оператор
в документе и форматирует весь документ через `ScriptDomSqlFormatter` (при ошибке форматирования
возвращается неотформатированная замена). Виды (`SqlTransformationKind`): `InsertToUpdate`
(однорядный VALUES + список колонок → SET с WHERE-заглушкой `1 = 1` и TODO-комментарием),
`ValuesToUnionAll` (левоассоциативная свёртка `BinaryQueryExpression` UNION ALL, псевдонимы
колонок первой строки), `ExecWithReturnCode` (`DECLARE @returnCode AS INT` + `EXEC @returnCode =`).
Неподходящие входы дают понятную ошибку (`SqlTransformationResult.Failed`).

Интеграция: команды `0x0250`–`0x0252` в обоих пакетах через общий фабричный метод
`AddTransformCommand`; предпросмотр — IdeShared `TransformationPreviewWindow` (было/станет);
применение — `TryApplyDocument` (весь документ, одна undo-транзакция).

Тесты: `SqlTransformerTests` — 16 сценариев (каждое преобразование на типовых входах,
замена только оператора, граничные отказы: без списка колонок/многорядно/DEFAULT VALUES/
уже захватывает код, ошибки разбора/каретки, контракты; результат перепроверяется парсером).

### 4.3. Генерация SQL по структуре таблицы — этап 8 *(выполнен)*

`src/TSqlFormatter.Core/Generation/`:

| Тип | Назначение |
|---|---|
| `TableColumn` | колонка: имя, полный текст типа (`NVARCHAR(50)`, `DECIMAL(18, 2)`, `NVARCHAR(MAX)`, пользовательские типы), NULL/NOT NULL, IDENTITY |
| `SqlTableDefinition` | схема (пустая → `dbo` в `SchemaOrDbo`), имя, колонки, span оператора `CREATE TABLE` |
| `TableDefinitionReader` | первый `CREATE TABLE` в скрипте или в заданном span-области (выделение); вычисляемые колонки пропускаются; без явного ограничения NULL колонка считается допускающей NULL (семантика T-SQL) |
| `CrudGenerator` | SELECT всех колонок; INSERT/UPDATE с параметрами (IDENTITY исключается); DELETE; заготовка `<схема>.usp_<имя>_Upsert` в отдельном batch после `GO`; WHERE-заглушки `1 = 1` с пометкой `/* TODO: key */`; вывод форматируется `ScriptDomSqlFormatter` профилем (fallback — неотформатированный текст) |

Ключевой нюанс: `CREATE PROCEDURE` обязан находиться в собственном batch — генератор
вставляет разделители `GO`, иначе ScriptDom даёт ошибку разбора и форматтер откатывается
к сырой заготовке.

Интеграция: команда `0x0260` «Сгенерировать CRUD по CREATE TABLE» в VS и SSMS — разбор
в фоне по снапшоту (область — выделение либо весь документ), предпросмотр
`TransformationPreviewWindow` (было — оператор CREATE TABLE, станет — сгенерированные
шаблоны), вставка через `TryApplyEdit` сразу после оператора одной undo-транзакцией.
Живое подключение к БД не используется — зафиксировано как ограничение этапа.

Тесты: `CrudGenerationTests` — 8 сценариев (схема/типы/NULL/IDENTITY, схема по умолчанию,
span-область, отсутствие CREATE TABLE и null-root, полный набор генерации, исключение
IDENTITY, только SELECT+DELETE без изменяемых колонок, контракты аргументов); контракт
меню — 12 кнопок.

### 4.4. История и окружения — этапы 9–10 *(этап 9 выполнен)*

**История редактора (этап 9).** Ядро в `src/TSqlFormatter.Core/History/`:
`EditorSnapshot` (путь, метка UTC, содержимое, отображаемое имя) и
`EditorSnapshotStore` — JSON-файлы по одному на снимок в
`%USERPROFILE%\.tsqlformatter\history` (`{version, filePath, timestampUtc, content}`),
имя файла — метка в локальном времени + хвост безопасного пути. Возможности:
`Save` (no-op при `Enabled = false` или контенте > `MaxSnapshotCharacters`),
`List` (новые сверху, битые файлы пропускаются), `Search` (подстрока в имени/пути/
контенте без учёта регистра), `Prune` (хранить `MaxSnapshots = 100` новейших,
запускается после каждого сохранения). Все операции best-effort: ошибки ввода-вывода
никогда не ломают вызывающий код.

Интеграция: оба пакета подписываются на события RDT (`AdviseRunningDocTableEvents`):
VS — существующий `SaveEventSink` в `HandleBeforeSave` (снимок читается из `docData`
через `IVsTextLines.GetLineText` до освобождения указателя и не требует активности
документа), SSMS — новый вложенный класс `RdtEvents` + собственный `HandleBeforeSave`
+ отписка в `Dispose` (best-effort по ADR 0005). Настройка полного отключения —
галочка `KeepEditorHistory` (по умолчанию включено) в `GeneralOptionsPage` (VS) и

не поддерживается — зафиксировано как ограничение.

до 200 тыс. символов), открытие выбранного снимка в новом документе через DTE
(`ItemOperations.NewFile("General\Text File")` + `TextDocument` edit point); при
