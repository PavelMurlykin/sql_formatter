# Дорожная карта доработки расширения (этапы)

План развития расширения T-SQL Formatter для Visual Studio 2022/2026 и SSMS 20/22
за пределами форматирования: статический анализ, инструменты редактора, генерация
SQL и возможности уровня SSMS. План основан на сравнении с SQL Prompt (Redgate) и
SQL Complete (Devart): форматтер готов и протестирован, поэтому новые возможности
строятся поверх существующей базы — ScriptDom-парсера (`src/TSqlFormatter.Core/Parsing/`),
дерева синтаксиса, позиций токенов и применения изменений в редакторе с Undo.

Каждый этап рассчитан на один автоматический запуск планировщика и завершается
коммитом и push. Документация по этапу обязательна (см. раздел «Документация» в каждом этапе).

## Правила выполнения этапов (протокол для каждого запуска)

1. Работай только в каталоге `C:\git\sql_formatter` и только в ветке
   `feature/extra_functions`. Никогда не переключайся на `main`, не пиши в него,
   не делай `force push`, не выполняй `reset --hard` и не изменяй настройки
   планировщика.
2. **Восстановление после сетевого сбоя.** Сначала выполни
   `git log @{u}..HEAD --oneline`. Если вывод не пуст — выполни `git push`
   (upstream уже настроен). После успешного push найди в таблице ниже этап со
   статусом «⏳ требует push», переведи его в «✅ завершён», при необходимости
   поправь дату в итоговой колонке, закоммить с сообщением
   `Этап N — повторный push после сбоя сети` и запушь. Это и есть работа
   текущего запуска: после успешного восстановления заверши запуск отчётом,
   новый этап не начинай.
3. **Выбор этапа.** Если незапушенных коммитов нет, выбери этап:
   первый со статусом «🔧 в работе» — продолжи его с того места, где остановился
   прошлый запуск (судя по состоянию рабочей копии и итоговой колонке);
   если таких нет — первый сверху со статусом «⬜ не начат». Если все этапы
   «✅ завершён» или «⚠ заблокирован» — ничего не реализуй, заверши запуск
   кратким отчётом о состоянии.
4. **Реализация.** Выполни работы раздела «Работы» выбранного этапа. Правила:
   - Вся новая логика — в `TSqlFormatter.Core` (netstandard2.0) или
     `TSqlFormatter.Configuration`, без зависимостей от IDE-типов (ADR 0003).
   - Интеграция в редактор — по образцу существующих команд
     (`src/TSqlFormatter.VisualStudio/SqlFormatterPackage.cs`, `ActiveSqlEditor`,
     `src/TSqlFormatter.IdeShared/`); для SSMS действует принцип best-effort (ADR 0005).
   - Не парси SQL в UI-потоке: снапшот текста → `Task.Run` → проверка актуальности,
     как в существующих командах форматирования.
   - На каждую новую логическую единицу — юнит-тесты в `tests/TSqlFormatter.Core.Tests`
     (или отдельный файл в существующем тестовом проекте).
5. **Сборка и тесты.** `dotnet build TSqlFormatter.sln` и
   `dotnet test TSqlFormatter.sln` должны проходить. Для этапов, меняющих VSIX,
   дополнительно `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Verify-Vsix.ps1`.
   Если полное построение VSIX на машине невозможно, зафиксируй причину в итоговой
   колонке и убедись, что сборка и тесты Core/Configuration/Cli проходят.
6. **Документация.** После реализации обнови (см. также раздел «Документация» этапа):
   - обязательно: `docs/development/technical.ru.md` и `docs/development/business.ru.md`
     (включая таблицы-журналы в конце каждого файла);
   - при изменении поведения, видимого пользователю: `docs/user-manual.ru.md`,
     `docs/user-manual.en.md` (согласованно, оба языка) и `CHANGELOG.md`.
7. **Статус и фиксация.** Обнови статус этапа в таблице ниже, дату и краткий итог.
   Затем `git add -A`, `git commit -m "Этап N — <название этапа>"`, `git push`.
   Если push не удался из-за сети — оставь коммит локально, поставь этапу статус
   «⏳ требует push» и заверши запуск отчётом: следующий запуск повторит push.
8. Один запуск — один этап. Не начинай следующий этап в этом же запуске.

Статусы: ⬜ не начат · 🔧 в работе · ✅ завершён · ⏳ требует push (коммит есть, push не прошёл) · ⚠ заблокирован (в итоговой колонке — причина).

## Фаза 1 — Статический анализ SQL (аналог SQL Code Analysis)

Приоритетное направление: использует готовый парсер и приносит пользу одновременно
в редакторе и в CI.

### Этап 1 — Ядро статического анализатора SQL

**Работы.**
- Новый каталог `src/TSqlFormatter.Core/Analysis/`: интерфейс `IAnalysisRule`,
  модель `AnalysisDiagnostic` (код правила, серьёзность Info/Warning/Error, сообщение,
  `SqlTextSpan` с позицией), `AnalysisOptions` (отключение правил по коду, переопределение
  серьёзности), фасад `SqlAnalyzer` (принимает `SqlParseResult`, обходит AST, собирает
  диагностику всех включённых правил).
- Первый набор правил (коды зафиксировать и использовать далее везде):
  - `TSQL001` — `SELECT *` в списке выборки (включая вложенные запросы);
  - `TSQL002` — `INSERT` без явного списка колонок;
  - `TSQL003` — `TOP`/`TOP (n)` без `ORDER BY` в том же запросе;
  - `TSQL004` — `UPDATE` без `WHERE`;
  - `TSQL005` — `DELETE` без `WHERE`.
- Сообщения на английском (единообразно с остальным Core), позиция — по началу
  соответствующего узла AST через line map.
- Юнит-тесты: срабатывание каждого правила, отсутствие ложных срабатываний
  (CTE с ORDER BY, UPDATE с WHERE и т.п.), отключение правила по коду,
  переопределение серьёзности.

**Критерии готовности.** `SqlAnalyzer` публичен и покрыт тестами; сборка и все
тесты решения проходят; поведение описано в технической документации (раздел 4.1).

**Документация.** technical.ru.md 4.1 (модель правил, коды, как добавить правило),
business.ru.md — ценность статического анализа; журналы обоих файлов.

### Этап 2 — CLI-проверка `--analyze`

**Работы.**
- В `src/TSqlFormatter.Cli` режим `--analyze` для stdin, файла и каталога
  (рекурсивно, как у существующих режимов): вывод замечаний в формате
  `путь(строка,столбец): TSQL00x [серьёзность] сообщение`.
- Коды выхода по образцу `--check`: 0 — замечаний нет, 1 — есть замечания,
  2 — ошибка разбора/ввода.
- Секция `analysis` в `.tsqlformatter.json` (отключённые правила, серьёзности),
  наследуется вместе с остальной конфигурацией при её поиске
  (`SqlFormatterConfigurationDiscovery`).
- Тесты CLI на файл/каталог/конфигурацию.

**Критерии готовности.** CLI анализирует все режимы ввода, коды выхода стабильны
для CI; тесты проходят; руководства пользователя (RU и EN) дополнены разделом
об анализе в CLI; CHANGELOG обновлён.

**Документация.** technical.ru.md 4.1 (CLI-контракт, формат вывода, секция конфигурации),
business.ru.md — сценарий CI-контроля качества SQL; user-manual.ru.md/en.md; CHANGELOG.

### Этап 3 — Анализатор в редакторе VS/SSMS

**Работы.**
- Команда «Анализировать документ» (меню Tools и контекстное меню редактора)
  в `TSqlFormatter.VisualStudio` и SSMS-адаптерах по образцу Format Document:
  снапшот текста → анализ в фоне → результат в UI-потоке.
- Отображение: маркеры-подчёркивания в редакторе для найденных позиций

- Настройки: включение/выключение анализа, управление правилами — добавить в

- VSIX для всех четырёх адаптеров собираются; `Verify-Vsix.ps1` проходит.

**Критерии готовности.** Команда работает по образцу существующих (не трогает

**Документация.** technical.ru.md 4.1 (интеграция в редактор, потоковая модель,

## Фаза 2 — Инструменты редактора

### Этап 4 — Сниппеты SQL

**Работы.**
- `src/TSqlFormatter.Core/Snippets/`: `SqlSnippet` (имя, ярлык, тело, параметры
  `$имя$`), `SnippetStore` — загрузка JSON-файлов из встроенного набора и каталога
  `%USERPROFILE%\.tsqlformatter\snippets` (создавать по требованию), `SnippetExpander` —
  раскрытие параметров, позиции для навигации.
- Встроенные сниппеты: шаблон процедуры (с заголовком и TRY/CATCH), TRY/CATCH,
  транзакция с ROLLBACK, шаблон SELECT с JOIN, INSERT заготовка.
- Команда «Вставить сниппет» в редакторе: выбор из списка (по ярлыку/имени),
  вставка с выделением первого параметра; повторная команда/Tab — переход к
  следующему параметру (если Tab-фильтр не удаётся встроить за этап — переход
  по команде, это зафиксировать в итоговой колонке).
- Тесты: загрузка стора, раскрытие параметров, слияние встроенных и пользовательских.

**Критерии готовности.** Вставка сниппетов работает в VS и SSMS-адаптерах,
пользовательские сниппеты подхватываются без перезапуска IDE (при следующей
команде); тесты и сборка проходят; руководства и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.2 (формат JSON сниппета, каталоги, порядок),
business.ru.md — ускорение написания типового SQL; user-manual.ru.md/en.md; CHANGELOG.

### Этап 5 — Переименование переменных и алиасов

**Работы.**
- `src/TSqlFormatter.Core/Refactoring/`: `RenameAnalyzer` — определение символа
  под позицией (локальная `@переменная` или алиас таблицы), поиск всех вхождений
  в рамках batch (для переменной) или запроса (для алиаса), включая вложенные
  запросы; результат — список `TextEdit` + предпросмотр «было → станет».
- Команда «Переименовать символ под курсором»: запрос нового имени (валидация
  для `@`-имён и идентификаторов), диалог предпросмотра изменений, применение
  одной undo-транзакцией по образцу форматирования.
- Тесты: переменные (объявление, ссылки, присваивание SET/SELECT), алиасы
  (внутри одного запроса, одноимённые алиасы в разных запросах не затрагиваются),
  отсутствие вхождений — понятная ошибка.

**Критерии готовности.** Переименование с предпросмотром и одной отменой работает;
тесты проходят; руководства и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.2 (границы области переименования),
business.ru.md — безопасный рефакторинг; user-manual.ru.md/en.md; CHANGELOG.

### Этап 6 — Структура скрипта и навигация

**Работы.**
- `src/TSqlFormatter.Core/Navigation/`: `ScriptOutlineBuilder` — дерево узлов
  (процедуры/функции/триггеры, batch, операторы, CTE, объявления переменных)
  с позициями; `SymbolLocator` — поиск объявления `@переменной` вверх по batch.
- Команда «Структура скрипта»: окно со деревом (Windows Forms по образцу
  `FormattingSettingsWindow`), двойной клик — переход к позиции в редакторе.
- Команда «Перейти к объявлению» для `@переменной` под курсором.
- Тесты: построение дерева на репрезентативном скрипте, поиск объявлений
  (ближайшее сверху в том же batch).

**Критерии готовности.** Обе команды работают; тесты проходят; руководства
и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.2 (модель дерева, правила поиска объявлений),
business.ru.md — навигация по длинным скриптам; user-manual.ru.md/en.md; CHANGELOG.

### Этап 7 — SQL-преобразования с предпросмотром

**Работы.**
- `src/TSqlFormatter.Core/Refactoring/Transformations`: ограниченный первый набор,
  каждый — функция AST → новый SQL-текст с последующим форматированием текущим
  профилем (`ScriptDomSqlFormatter`):
  - `INSERT INTO t (…) VALUES (…)` → `UPDATE t SET …` (колонка=значение, WHERE-заглушка);
  - многорядный `VALUES` → `SELECT … UNION ALL SELECT …`;
  - `EXEC proc …` → `DECLARE @rv …; EXEC @rv = proc …` (перехват кода возврата).
- Команды редактора «Преобразовать: …» с диалогом предпросмотра результата
  (до/после), применение одной undo-транзакцией.
- Тесты: каждое преобразование на типовых и граничных входах, идемпотентность
  форматирования результата.

**Критерии готовности.** Не меньше двух преобразований работают end-to-end;
тесты проходят; руководства и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.2 (контракты преобразований, как добавить новое),
business.ru.md — экономия времени на рутинных переработках; user-manual.ru.md/en.md; CHANGELOG.

## Фаза 3 — Метаданные БД и возможности SSMS

### Этап 8 — Генерация CRUD по таблице

**Работы.**
- `src/TSqlFormatter.Core/Generation/`: `TableDefinitionReader` — разбор
  `CREATE TABLE` (в буфере или выделении) в модель колонок (имя, тип, NULL/NOT NULL),
  `CrudGenerator` — генерация SELECT/INSERT/UPDATE/DELETE и заготовки хранимой
  процедуры (параметры по колонкам), результат прогоняется через форматтер.
- Команда «Сгенерировать CRUD по CREATE TABLE»: если в документе/выделении есть
  CREATE TABLE — показать предпросмотр и вставить в документ (или новый файл).
- Полное подключение к живой БД — вне этапа (зафиксировать как ограничение).
- Тесты: разбор CREATE TABLE (включая IDENTITY, NULL, типы с размерностью),
  генерация всех четырёх операторов и процедуры.

**Критерии готовности.** Генерация из CREATE TABLE работает; тесты проходят;
руководства и CHANGELOG обновлены; ограничение «без живого подключения» отражено.

**Документация.** technical.ru.md 4.3 (модель таблицы, правила генерации),
business.ru.md — ускорение написания типового кода доступа; user-manual.ru.md/en.md; CHANGELOG.

### Этап 9 — История редактора и восстановление

**Работы.**
- `src/TSqlFormatter.Core/History/` + интеграция: `EditorSnapshotStore` — локальные
  снимки открытых `.sql` документов в `%USERPROFILE%\.tsqlformatter\history`
  (имя файла, сервер/БД при доступности, метка времени, содержимое; ротация по
  возрасту/количеству, настройка-лимит).
- Снятие снимков: по сохранению и закрытию документа (по образцу `SaveEventSink`;
  для несохранённых — при закрытии с отказом от сохранения, насколько позволяют API).
- Команда «Восстановить закрытый скрипт»: диалог истории с поиском по тексту/имени,
  предпросмотр, открытие восстановления в новом документе.
- Приватность: всё строго локально; настройка полного отключения истории.
- Тесты: хранилище (сохранение, ротация, поиск) в Core; поведение интеграции —
  по возможности смоуком.

**Критерии готовности.** Снимки пишутся локально, восстановление работает; тесты
проходят; руководства и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.4 (формат снимков, ротация, приватность),
business.ru.md — защита от потери кода; user-manual.ru.md/en.md; CHANGELOG.

### Этап 10 — Окружения и защита от опасных команд

**Работы.**
- `src/TSqlFormatter.Configuration`: модель окружений — правила сопоставления
  сервера/БД (подстрока имени сервера из moniker документа/подключения) метке
  DEV/TEST/PROD и цвету; настройка в существующих страницах настроек, минимально.
- Команда/индикация: определение окружения активного документа, цветовая метка
  (доступный механизм: полоса в диалогах, заголовок окна структуры или статусная
  строка; окрашивание вкладки — best-effort через доступные API, при неудаче
  зафиксировать в итоговой колонке, это соответствует ADR 0005).
- Команда «Проверить опасные команды»: анализ документа на `DROP`/`TRUNCATE`/
  `UPDATE`/`DELETE` без WHERE (поверх правил Этапа 1), диалог-предупреждение
  с перечнем и позициями; для PROD-окружения — акцентированное предупреждение.
  Перехват самого выполнения запроса — вне этапа.
- Тесты: сопоставление окружений, детекция опасных команд.

**Критерии готовности.** Окружения настраиваются и определяются, проверка опасных
команд работает; тесты проходят; руководства и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.4 (правила окружений, границы интеграции),
business.ru.md — защита от ошибок в продуктиве; user-manual.ru.md/en.md; CHANGELOG.

### Этап 11 — Работа с результатами запросов

**Работы.**
- Команды работы с табличными данными из буфера обмена (TSV, скопированный из
  грида результатов SSMS/VS): «Вставить как IN (…)», «Сформировать INSERT»
  (с именем целевой таблицы из диалога), результат форматируется текущим профилем;
  «Статистика выделенного» — сумма/количество/среднее числовых ячеек TSV.
- Прямой доступ к гриду результатов (COM ResultsGrid) — вне этапа: работа строится
  на буфере обмена, что покрывает основной сценарий и не зависит от внутренних
  API SSMS (зафиксировать как осознанное ограничение).
- Тесты: преобразование TSV → IN/INSERT (типы: числа, строки, NULL, даты),
  статистика (пропуск нечисловых).

**Критерии готовности.** Команды работают в SSMS-адаптерах и VS; тесты проходят;
руководства и CHANGELOG обновлены.

**Документация.** technical.ru.md 4.5 (модель TSV-преобразований),
business.ru.md — перенос данных между запросами; user-manual.ru.md/en.md; CHANGELOG.
