# План развития форматтера: покрытие параметров SQL Complete

Статус: SC-01–SC-07 завершены 2026-09-29; следующий этап — SC-08. Дата базовой сверки: 2026-09-29.

Этот файл — самостоятельная очередь новых работ. Завершённые этапы 0–30 остаются в `CODEX_DEVELOPMENT_PLAN.md` как история; для выбора следующей задачи перечитывать их не требуется. Следующий этап — первый с отметкой `[ ]`. Статус этапа меняется на `[x]` только после выполнения его критериев приёмки; если этап заблокирован, причина и оставшиеся пункты фиксируются здесь.

## Цель и границы

Целевое состояние: пользователь может настроить в нашем приложении форматирование всех конструкций и всех параметров, представленных в двух переданных профилях SQL Complete, получить предсказуемый результат из Core, CLI, Visual Studio и поддерживаемого SSMS, сохранить собственный профиль и воспроизвести его на другом компьютере. «Покрытие» означает **семантически эквивалентную управляемую возможность**, а не копирование кода, алгоритмов, интерфейса или формата хранения SQL Complete и не обещание побайтово идентичного вывода для любого T-SQL.

Оба XML используются как референс требований, включая параметры, которые в них выключены и не отличаются друг от друга. Их числовые режимы (`0`, `1`, `2`, `8`, `Style` и т. п.) нельзя интерпретировать по догадке: семантику нужно подтвердить на контрольных SQL-примерах. Если конкретная конструкция зависит от версии T-SQL, правило должно быть доступно при подходящем диалекте, а не молча игнорироваться.

Объединённый реестр должен учитывать **577 верхнеуровневых узлов и 977 различных путей скалярных значений**, включая 203 группы `SubOptions`. Вложения из `.codex-remote-attachments/` не считать долговечным источником: в SC-01 сохранить проверенные, обезличенные исходники или воспроизводимый нормализованный снимок в репозитории с согласованным происхождением.

Текущая отправная точка: Core имеет 16 полей настроек в разделах `General`, `Indent`, `Keywords`, `Select`, `Clauses`, `Joins`, `Where`, `Alignment`; JSON версии 1 и страницы IDE покрывают лишь часть из них. Простые формы `SELECT`, DML, `CASE`, CTE, подзапросов и хранимого кода уже форматируются, но часто по фиксированным правилам. XML-профили SQL Complete не импортируются. Это описание — ориентир, а не список выполненных шагов нового плана.

## Контракт каждого этапа

1. Работать по следующему незавершённому `SC-xx`, не объявляя весь раздел T-SQL поддержанным после нескольких примеров. Для каждого параметра этапа записывать в реестр: XML-путь, значение обоих профилей, смысл и область действия, нативное имя/тип/значение по умолчанию, связь с другими опциями, тесты и статус. Значения `неизвестно` допустимы временно, но не при закрытии соответствующего этапа.
2. Любое новое правило имеет позитивные и негативные тесты, два варианта настроек с различимым результатом, проверки сохранности литералов/комментариев, повторного разбора, идемпотентности и безопасного отказа на неподдержанной форме. Для взаимозависимых переключателей тестировать допустимые комбинации, а не только отдельное поле.
3. Настройки действуют одинаково в Core и через адаптеры. Старый JSON v1 продолжает читаться с прежней семантикой; миграция и приоритеты переопределений покрываются тестами. Режимы со специфическими для конструкции отступами не должны незаметно менять остальные конструкции.
4. На каждом **этапе реализации** обновлять `docs/user-manual.ru.md` и `docs/user-manual.en.md` по фактическому поведению, запускать применимые сборку/тесты и давать готовый текст сообщения коммита. Коммит и push выполнять после каждого этапа, когда это прямо запрошено пользователем; не считать их частью одного лишь составления плана.
5. Любое осознанное отличие от SQL Complete фиксировать как решение с примером и проверкой в реестре. Статус `покрыто` допустим только при работающей нативной настройке или документированной эквивалентной композиции; «есть поле JSON, но оно не влияет на вывод» не считается покрытием.

## Этапы

### Основа и общие механизмы

- [x] **SC-01 — Проверяемый реестр требований.** Завершён 2026-09-29. В `tests/TSqlFormatter.Core.Tests/SqlCompleteParity/` сохранены обезличенный нормализованный снимок `profile-values.tsv`, изменяемый реестр `coverage.tsv` с явным статусом `pending_semantics` для каждого пути и 20-категорийный `corpus.tsv`. `scripts/Sync-SqlCompleteParityInventory.ps1` по SHA-256 сверяет снимок с приложенными XML, включая 577 узлов, 203 вложенные группы, 977 путей и 190 различающихся общих значений; unit-тесты проверяют снимок и разбираемость примеров. Исходные XML в репозиторий не скопированы, новые пользовательские настройки этим этапом не добавлены.
- [x] **SC-02 — Нативная модель конфигурации v2.** Завершён 2026-09-29. Добавлены типы булевых, целых, перечислимых, пороговых и локальных правил отступа; каталог хранит область, зависимости, диалект, ограничения и значения по умолчанию. JSON v2 хранит типизированные `rules`, проверяет ошибки без частичного применения и сохраняет переопределения при наложении настроек. JSON v1 и его обычная сериализация остаются совместимыми; `SerializeV2` мигрирует старые настройки. Каталог встроенных новых правил пока пуст — поведение форматтера не менялось.
- [x] **SC-03 — Универсальные примитивы раскладки.** Завершён 2026-09-29. `SqlLayoutPolicy.Resolve` объединяет независимые поля в порядке общие → оператор → предложение → локальное; `SqlLayoutPrimitives` содержит переносы, списки с обеими позициями запятой, скобки и безопасное выравнивание. `ListClauseDocBuilder` использует общий механизм списков без изменения прежнего вывода. Тесты проверяют приоритеты, ширину, комментарии и безопасный отказ от выравнивания; новые пользовательские параметры не включены.
- [x] **SC-04 — `TextCase`.** Завершён 2026-09-29. JSON v2 содержит семь независимых правил регистра; классификация функций, типов и алиасов опирается на ScriptDom AST, литералы и комментарии не затрагиваются. Для совместимости v1 имена и заключённые в кавычки идентификаторы по умолчанию сохраняются; изменение регистра имён требует явной настройки и может быть небезопасно для баз с чувствительной к регистру сортировкой. Числовые режимы XML не импортируются: используются описательные нативные значения `inherit`/`preserve`/`upper`/`lower`.
- [x] **SC-05 — `Spacing`.** Завершён 2026-09-29. Десять независимых правил JSON v2 управляют пробелами у запятой, точки, `::`, бинарных арифметических операторов и скобок вызова функций. Нативные значения `inherit`/`insert`/`remove` заменяют нерасшифрованные числовые режимы XML; изменения применяются только к однострочным межтокенным промежуткам. После изменения проверяются повторный разбор и неизменность последовательности токенов; литералы, комментарии и унарные операторы не переписываются.
- [x] **SC-06 — Общие списки и разделители пакетов.** Завершён 2026-09-29. Нативные правила управляют ведущей/концевой запятой и пробелом после ведущей запятой в вертикальных списках, а также включением и расположением пустой строки у `GO`. Общий постпроцессор действует на списки разных конструкций после примитивов раскладки, проверяет повторный разбор и последовательность токенов; по умолчанию не меняет прежний результат. Поддержан отдельный `GO` без счётчика повторов; `GO 2` ScriptDom в проверенном примере не разобрал.

## Правило продолжения

При запросе «следующий этап» брать первый `[ ]` из этого файла, реализовывать только его и обновлять здесь статус и краткий результат. Если этап открывает новый параметр без проверенной семантики, сначала получить контрольный вывод или зафиксировать измеримый способ её установить; не подменять неопределённость предположением. Старый общий план нужен лишь при изменении архитектурных принципов или для исторической справки.
